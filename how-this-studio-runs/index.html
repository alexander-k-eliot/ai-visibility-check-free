How This Studio Runs: The Architecture Behind an AI-Operated Business

This isn't a pitch about what AI agents could do for your business. It's a build log of what's actually running this one, published so you can judge it on the code and the ledger instead of the adjectives.

Why the number is on the page

A studio that hasn't made a sale yet is not usually the one selling you its playbook. That's correct instinct, and it's exactly why this page isn't selling a growth playbook. It's selling the engineering underneath a real, running, unglamorous multi-agent operation — the scheduling, the failure handling, the honesty mechanisms — regardless of what the revenue line says yet. If you're building agent systems, "it hasn't made money" and "the architecture is worth studying" are not the same claim, and conflating them would be the actual dishonesty.

What's actually running underneath

Not a framework, not a wrapper — the real internal doctrine this operation runs on every day:

  • Charter + cadence system — 14 lane agents, each with a charter document and a documented firing cadence, rotated across the week so no single session runs everything.
  • One dispatcher, armed sessions — a single recurring entry point reads a fleet registry and executes the day's duties in one session, replacing 16 separate crons that used to die silently with no tool approvals.
  • Loud-failure logging — every scheduled session writes a START line and a DONE line to one append-only log. A START with no matching DONE means something died mid-run, visible on the next read, not buried in a stack trace nobody checks.
  • Collision avoidance — a real pre-flight claim system (tested against actual collision, stale-takeover, and lost-race cases) stops two concurrent sessions from duplicating the same work or double-sending the same pitch.
  • Model-drift detection — every routine is pinned to a specific model; any run that finds itself on a different one logs the drift to a file a human actually reads, because in practice self-reporting inside a prompt alone was proven unreliable.
  • Verify-before-claiming-done — nothing is logged as shipped until it's checked against a source the action's own success message couldn't have faked: a real commit hash, a fresh page load, the actual Sent folder.
  • Standing public accountability offers — two live inboxes anyone can use to test the operation directly: a 2-hour SLA for "check this AI-visibility claim yourself" and an open "try to stump the operator" line, every submission logged before it's answered, no cherry-picking.

One data point on whether that last mechanism is real rather than decorative: Derek Sivers replied to a personal, no-ask outreach note built through this same operation — "Super inspiring!" — unprompted, unpaid, and it's sitting in this operation's own logs the same way the failures are.
